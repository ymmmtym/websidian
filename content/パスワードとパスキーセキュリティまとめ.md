## 概要

パスワード強度の目安とハッシュの仕組みから、攻撃パターン（フィッシング・脆弱性悪用）、GMO関連および大手サービスのインシデント事例、パスキーの仕組み、保存先の選び方と移行、vaultwardenの対応状況までを1本にまとめた記録。Apple デバイス + Android（OPPO）の2台体制でパスキーの保存先を整理したい人を対象とする。

## パスワード解読にかかる時間の早見表

## なぜハッシュ化してもパスワードは漏れるのか

### 核心

**ハッシュそのものは元に戻せない。** しかし攻撃者は「戻す」のではなく、**手元で片っ端から試して、同じハッシュになる元の文字列を探す**ことで割り出す。暗号解読ではなく、**高速な総当たり（答え合わせ）**である。

### 直感：ミキサーと答え合わせ

ハッシュ関数はミキサーである。りんご + バナナ → ミックスジュース（ハッシュ値）は作れても、ジュースからりんごは復元できない（不可逆性）。

しかし攻撃者の手元に**漏洩したジュース**と**超高速ミキサー**があれば、

1. 「password123」をかける → 味が違う
2. 「tokyo2024」をかける → 味が違う
3. 「sakura0401」をかける → **同じ味が出た** → 元は sakura0401 と判明

サーバーへのログイン試行ではないので、**「3回間違えたらロック」は一切効かない**。攻撃者は手元の GPU を回しているだけである。

### 代表的な攻撃手法

1. **辞書攻撃・総当たり**: 数十億件規模のパスワード辞書を上から順に照合
2. **レインボーテーブル**: 平文⇄ハッシュの巨大な対応表を事前に作り、検索するだけで特定
3. **ハッシュが「速すぎる」**: SHA-256 や MD5 はファイル改ざん検知用に高速設計。GPU なら毎秒数十億〜数百億回の計算が可能

### 防御側の対策

- **ソルト（Salt）**: ランダムな文字列を付加してからハッシュ化（`hash("password" + "abc!9z")`）。事前計算表を無効化
- **ストレッチング**: 意図的に計算を重くする低速 KDF（**Argon2**、**bcrypt**、**PBKDF2**）。1回の検証に 0.1 秒かけても、1億通り試すには約115日かかる

### 参考実測値

この環境（1コア・Python 実装）で計測した目安である。実際の GPU 攻撃はさらに数桁高速だが、**高速ハッシュと低速 KDF の差の桁**を見るための数字である。

| 条件 | 結果 |
|---|---|
| SHA-256 の処理速度 | 約 128 万回/秒 |
| PBKDF2（21万回反復）1件あたり | 約 0.047 秒 |
| 候補 1,000 万語を1アカウントに対し SHA-256 で試す | 約 7.8 秒 |
| 同じ条件を PBKDF2（21万回）で試す | 約 5.4 日 |

**同じ「試行」でも、方式ひとつで 5 桁以上変わる**ことが分かる。だからこそ「何のハッシュ関数を使っているか」が事故の大きさを決める。

### それでも漏れる理由

- **古いシステムがそのまま動いている**（ソルトなし MD5 / SHA-1 / 素の SHA-256）
- **パスワード自体が単純すぎる**（「123456」は試行の最初の方で当たる）
- **使い回し**（1か所で破られると、銀行・メール・SNS へ波及 = クレデンシャルスタッフィング）

### パスキーとの決定的な違い

パスワードは「**人間が覚えられる短い文字列**」だからこそ、ハッシュ化しても総当たりで推測される。パスキーの鍵は「**人間が覚える必要のない、長くランダムな巨大な数**」なので、総当たりそのものが成立しない。

## 最近のセキュリティインシデントの主な原因

### ブルートフォース攻撃は主な原因ではない

IPA「情報セキュリティ10大脅威 2025（組織編）」のランキング：

| 順位 | 脅威 |
|---|---|
| 1位 | ランサム攻撃による被害 |
| 2位 | サプライチェーンや委託先を狙った攻撃 |
| 3位 | システムの脆弱性を突いた攻撃 |
| 4位 | 内部不正による情報漏えい等 |
| 5位 | 機密情報等を狙った標的型攻撃 |

ブルートフォース攻撃は上位5位には入っていない。

### ランサムウェア侵入原因の内訳（デジタルアーツ調査）

2024年1月〜2025年5月の国内ランサムウェアインシデント38件の分析：

| 侵入原因 | 割合 |
|---|---|
| 脆弱性の悪用 | 39%（15件） |
| 認証情報の悪用 | 34%（13件） |
| 設定不備（ブルートフォースを許す等） | 残り |

「認証情報の悪用」の34%の多くは、**フィッシングやインフォスティーラー（情報窃取マルウェア）による資格情報の窃取**であり、パスワードを1文字ずつ総当たりで解読するブルートフォースそのものではない。

### なぜブルートフォースは主な原因ではないのか

1. **フィッシング・インフォスティーラーが主流**: パスワードを「解読」するのではなく、そのまま盗む手法が圧倒的に効率的
2. **脆弱性の悪用が最も多い**: VPN装置やリモートデスクトップ製品の未修正脆弱性を突く攻撃が主流
3. **ブルートフォースは対策が容易**: ログイン試行回数制限、CAPTCHA、多要素認証（MFA）などで効果的に防げる
4. **サービスアカウントの侵害が85%**: ReliaQuestの調査では、インシデントの85%に「侵害されたサービスアカウント」が関与。これはブルートフォースではなく、漏洩した認証情報の悪用

## フィッシングと脆弱性の悪用

### フィッシング（Phishing）

**仕組み**: 攻撃者が銀行、SNS、会社のシステムなどを装った偽のWebサイトやメールを送り、ユーザーにパスワードや認証コードを入力させる。

**具体例**:
- 「Amazonからの支払いエラー通知」というメールに、本物そっくりのログイン画面へのリンク
- 社内のITサポートを装った「パスワードの有効期限が切れました」というメール
- 偽のMicrosoft 365ログイン画面で社員の資格情報を盗む

**ポイント**: 技術的な防御を完全にすり抜ける。パスワードが32文字でも128文字でも、本人が入力してしまえば意味がない。

### 脆弱性の悪用（Vulnerability Exploitation）

**仕組み**: システムやアプリケーションのバグや設計ミスを突いて、本来許可されていない操作を行う。

| 攻撃の種類 | 仕組み |
|---|---|
| SQLインジェクション | ログインフォームに特殊な文字列を入力して、データベースに不正な命令を送る |
| XSS（クロスサイトスクリプティング） | 掲示板やコメント欄に悪意あるスクリプトを埋め込み、閲覧者のブラウザで実行させる |
| コマンドインジェクション | 入力欄にOSコマンドを注入してサーバー上で実行させる |
| パストラバーサル | `../../etc/passwd` のような入力で、本来見られないファイルにアクセス |
| RCE（リモートコード実行） | ソフトウェアのバグを突いて、攻撃者が任意のコードをサーバー上で実行 |

**ポイント**: パスワードの強度とは無関係。システム側の脆弱性を突くため、ユーザーが強いパスワードを使っていても関係なく侵入される。

### 両者の違い

| 項目 | フィッシング | 脆弱性の悪用 |
|---|---|---|
| 標的 | 人間（ユーザー） | システム・ソフトウェア |
| パスワード強度との関係 | 無関係（盗まれる） | 無関係（迂回される） |
| 対策の主体 | ユーザー教育、メールフィルタリング | 開発者・運用者（パッチ適用、セキュアコーディング） |
| 多要素認証（MFA）で防げるか | 部分的に有効 | 無効 |

### 強いパスワードは何のため？

強いパスワードはあくまで以下の場面で有効：
1. パスワードデータベースが漏洩したとき（オフライン攻撃に耐える）
2. 推測されやすいパスワードを使わない（辞書攻撃に耐える）
3. 同じパスワードを使い回さない（一箇所の漏洩が他に波及しない）

ただし、**フィッシングや脆弱性の悪用には直接関係ない**。

## パスキーの仕組み

### 一言で

パスキーは「パスワードの代わりに、**端末の中にしまった秘密鍵**でログインする仕組み」である。サーバーには公開鍵だけが置かれ、ログインのたびに「今この瞬間のチャレンジ」に秘密鍵で署名して送り返す。秘密そのものは一度もネットワークを渡らない。

### 直感：合言葉とサインの違い

- **パスワード = 合言葉**。知っている人全員が同じ言葉を言えるので、盗み聞きや偽の受付に弱い。
- **パスキー = その場で書くサイン**。偽の受付では、手元のペンが「この用紙は本物か」を確認しないと動かない。しかもサインは毎回変わるのでコピーできない。

> **比喩の限界**: 指紋や顔認証はパスキーそのものではありません。生体認証は「大事なペンを取り出すための引き出しの鍵」であり、サーバーに送られるのは指紋ではなく署名です。ここが最も混同されやすい点です。

### 登録の流れ（最初の1回）

1. サーバーが「チャレンジ（毎回変わる乱数）」と「どのサイト用か（rpId = ドメイン名）」をブラウザに渡す
2. 端末がそのサイト専用の**鍵ペア**を生成。デバイス固定型の秘密鍵は端末の安全領域（iPhone なら Secure Enclave、Android なら TEE など）に、外に出せない形で保管される。同期型の秘密鍵は暗号化された状態で別端末へ同期される
3. **公開鍵だけ**をサーバーに送り、アカウントに保存

### ログインの流れ（2回目以降）

1. サーバーが新しいチャレンジを送る
2. 端末が生体認証などで鍵を開け、**チャレンジ + ドメイン名**に対して秘密鍵で署名（アルゴリズムは ES256 など）
3. サーバーが保存しておいた公開鍵で署名を検証。合っていれば本人

### なぜ強いのか（3点）

| 性質 | 効いている仕組み |
|---|---|
| **盗んでも再利用できない** | チャレンジが毎回変わるため、過去の署名を再生できない（リプレイ攻撃不可） |
| **偽サイトで使えない** | 署名がドメイン名に縛られているため、偽ドメインでは有効な署名が作れない（フィッシング耐性） |
| **漏れても他に波及しない** | サーバーにあるのは公開鍵だけ。公開鍵から秘密鍵は逆算できない |

### 端末を替えたとき

- **同期型パスキー**: iCloud キーチェーン / Google パスワードマネージャなど。クラウドで同期され、エンドツーエンド暗号化されるため事業者にも中身は見えない。機種変更してもそのまま使える
- **デバイス固定型パスキー**: USB セキュリティキーなど。その端末に固定される

### パスキーならGMO事例のような被害は防げた

| 項目 | 従来のパスワード | パスキー |
|---|---|---|
| 認証情報の保存場所 | サーバー側にハッシュとして保存 | 端末内に秘密鍵を保持（サーバーには公開鍵のみ） |
| サーバー漏洩時の影響 | ハッシュが漏洩 → オフライン攻撃で解読される可能性 | 公開鍵だけでは何もできない |
| GMO事例でのリスク | サーバー上のファイルからパスワードが丸見え | 秘密鍵は端末内なので、サーバー侵害でも漏洩しない |

### パスキーの核心

> **「認証の秘密をサーバーから端末に移動させた」**

これだけで、サーバー侵害による認証情報漏洩という被害を原理的に防ぐことができる。

### 守れる脅威と残るリスク

```
従来のパスワードの弱点：
├─ サーバー漏洩 → パスワードが盗まれる
├─ フィッシング → 人間が入力してしまう
├─ 使い回し → 一箇所の漏洩が他に波及
└─ 推測されやすい → 辞書攻撃で破られる

パスキーで解決できるもの：
✓ サーバー漏洩 → 解決（秘密鍵は端末内）
✓ フィッシング → 大幅に軽減（ドメイン紐付けで偽サイトを検出）
✓ 使い回し → 解決（サービスごとに固有の鍵ペア）
✓ 推測 → 解決（暗号学的に生成される乱数）

パスキーでも残るリスク：
△ 端末の紛失・盗難
△ Apple/Googleアカウントの侵害
△ 端末内の高度なマルウェア
△ サービス側の未対応
```

### 限界・注意点

- **端末とアカウントを両方失うと詰む**。復旧用の別経路（別端末のパスキー、リカバリーコード）が前提
- **共有端末には向かない**。同期型は「あなたのクラウドアカウント」に紐づくため
- **パスキー = パスワードレスとは限らない**。2要素認証の「持っているもの」として使う設定もある
- **サイト側が対応していないと使えない**

### パスワードとの比較

| 観点 | パスワード | パスキー |
|---|---|---|
| サーバーが持つ情報 | 共有秘密（ハッシュ） | 公開鍵のみ |
| 漏洩時の影響 | 使い回しで他サイトにも波及 | 実質ゼロ（署名は作れない） |
| フィッシング | 偽サイトに入力してしまう | ドメインが違えば署名できない |
| 覚えるもの | 文字列 | なし（端末が持つ） |

## 保存先を Apple と Google どちらに統一するか

### 結論

- **Apple に寄せると、メインの Android（OPPO）で使えなくなるため非推奨**
- 無料で済ませるなら **Google パスワードマネージャ**
- Mac の Safari も使いたいなら **1Password**（無料枠なら Bitwarden も可）

ただし「統一」より優先すべき前提がある。**パスキーはファイルでコピーして移せるとは限らない**。Google は Android から対応する他社パスワードマネージャへのエクスポート手順を公開しており、Apple も iOS 26 / macOS 16 でインポート/エクスポートに対応する。保存先と OS の組み合わせによっては移行できるが、まだ使えない場合もあるため、整理の実体は「各サービスで登録し直す」作業になる。

### 3案の比較

| 項目 | Apple パスワード（iCloud） | Google パスワードマネージャ | 1Password |
|---|---|---|---|
| 同期される範囲 | Apple 製端末のみ | Android・Chrome（Mac/Windows/Linux） | iPhone・Android・Mac・Windows・Linux |
| Android（OPPO）での利用 | 同期は不可（近くの iPhone に保存したパスキーを QR コード経由で使う方法はある） | 可 | 可 |
| Mac の Safari での利用 | 可 | 不可 | 可（認証情報プロバイダ対応） |
| Mac の Chrome での利用 | 可（拡張機能経由） | 可 | 可 |
| 料金 | 無料 | 無料 | 有料（個人 月約 $2.99） |

### なぜ Apple に寄せると詰むのか

パスキーは**登録したときのブラウザ / OS が保存先を決めてしまう**のが根本である。Apple パスワード（旧 iCloud キーチェーン）は**同じ Apple アカウントの Apple 製端末の間でしか同期しない**。他プラットフォームとの互換は広がっていない、と Chrome の開発ブログでも明言されている。

一方 Google パスワードマネージャは、**Chrome にサインインしていれば macOS・Windows・Linux・Android のどこでも同じパスキーを作成・同期**できる。

弱点は、**Mac の Safari からは Google パスワードマネージャのパスキーが出てこない**こと。Safari が使うのは Apple 側か、Apple の「認証情報プロバイダ」に対応したアプリ（1Password など）だけである。

### パスワード vs パスキーの移行性の違い

| 項目 | パスワード | パスキー |
|---|---|---|
| Google → Apple間の移行 | CSVエクスポート/インポートで可能 | Android では対応他社マネージャへのエクスポート可。Apple 側のインポート対応は iOS 26 / macOS 16 以降 |
| Apple → Google間の移行 | CSVエクスポート/インポートで可能 | Apple のエクスポートに対応した OS では移行可。それ以外は直接移行不可 |
| 移行の現実的な方法 | ファイルで一括移行 | 保存先と OS の組み合わせに依存。移行できない場合はサービスごとに再登録が必要 |

### 近未来の改善

- **Google Password Manager**: Android から対応する他社パスワードマネージャへのパスキーエクスポート手順を公開している
- **Apple**: WWDC 2025でパスキーのインポート/エクスポート機能を発表。iOS 26、macOS 16などの次期メジャーリリースで利用可能になる見込み

### 実務的な進め方

1. **主系を1つ決める**
   Mac も Android も Chrome 中心 → Google。Safari を手放せない → 1Password（または Bitwarden）。
2. **「全部移す」を目標にしない**
   パスキーは**1つのアカウントに複数登録できます**。理想は「主系1つ + 予備1つ」。散らかって見える原因は保存先が2つあることではなく、**どこに何があるか把握できていないこと**。まず一覧を作る。メール・銀行・SNS・決済など、落としたら痛いものから。
3. **移行は「追加 → 確認 → 削除」の順**
   新しい保存先でパスキーを追加し、**別の端末で実際にログインできることを確認してから**古いほうを削除。逆順にするとロックアウトする。パスワードと2要素認証の経路は消さずに残す。
4. **移行の標準化は進行中**
   FIDO の Credential Exchange（CXF）という、保存先間でパスキーを移すための標準仕様が整備されつつあり、Google パスワードマネージャとサードパーティ製マネージャ間の直接インポート / エクスポートも登場している。全部を手作業で移す必要は、数年単位で見れば減っていく。

### 今すぐGoogle主体に移行する実践的な方法

**方法1：サービスごとに再登録（現状最も確実）**
1. 各サービスのログイン画面で「パスキーを追加」または「パスキーでログイン」
2. Android端末のGoogle Password Managerに保存するよう選択
3. 以前のパスキー（iCloud Keychain側）は削除

**方法2：新規登録時にGoogle側で作成**
- これから新しくパスキーを設定するサービスは、必ずAndroid端末 + Google Password Managerで作成
- 古いパスキーは使なくなった段階で削除

### 移行の優先順位の提案

```
優先度1（今すぐ）:
└─ 金融系（SBI証券など）→ 最も重要なのでGoogle側に再登録
└─ 主要なメール・アカウント

優先度2（数週間以内）:
└─ よく使うSNS・ショッピングサイト

優先度3（Appleのパスキーをそのまま残す）:
└─ 移行が面倒で、iPhone/Macでしか使わないサービス
```

### 複数パスキーの管理について

パスキーはサービスごとに独立した鍵ペア（公開鍵・秘密鍵）を生成する。

```
パスキーA（Apple）: 秘密鍵A → iCloud Keychain
                 公開鍵A → サービス側

パスキーB（Google）: 秘密鍵B → Google Password Manager
                 公開鍵B → サービス側
```

**重要**: 秘密鍵Aが漏洩しても、秘密鍵Bには影響しない。暗号学的には完全に独立している。

**複数パスキーの問題点**:
- **管理の複雑化**: 「どのパスキーがどこに保存されているか」が混乱しやすい
- **不要なパスキーの放置**: 使わなくなったパスキーが残り続けると紛失・侵害時の把握が難しくなる
- **サービス側の管理負荷**: 公開鍵が複数登録されるため、整理が必要

**推奨される状態**:

| 状況 | 推奨 |
|---|---|
| 同じ用途でAppleとGoogleの両方に同じパスキー | 不要。どちらか1つに絞る |
| メイン端末用 + バックアップ用（ハードウェアキー等） | 推奨。用途が異なるので問題なし |
| 古い端末に残ったパスキー | 削除すべき |
| 移行中で新旧のパスキーが共存 | 移行完了後、古い方を削除 |

**理想は「1サービスあたり2つ以内」（メイン + バックアップ）が最もクリーン。**

### 注意点

- **共有端末では同期型パスキーが使いにくい**（自分のクラウドアカウントに紐づくため）
- **1Password は Secret Key を失うと復旧できない**（Emergency Kit の保管が前提）
- **iPhone も併用している場合**は話が変わる。iPhone があるなら「Mac は Safari、外は iPhone」で完結するので、Google に寄せるより iCloud 維持のほうが楽になる可能性がある

## GMO関連セキュリティインシデント事例

### 事例1：2026年10月「お名前.com デスクトップクラウド」不正アクセス事案

**概要**: 2026年10月20日、GMOインターネットのサービス「お名前.com デスクトップクラウド」に不正アクセスがあり、26,739台のサーバーに影響の可能性があった（第3報時点。不正アクセスや情報取得が確認された件数ではない）。

**何が起きたか**:
- 一部のサーバーに不正なプログラムが設置され、顧客が保管していた情報が閲覧された
- 証券会社・FX会社の取引ツール（MT4/MT5等）に関連する口座のパスワードなどの認証情報が第三者に閲覧された可能性がある
- 複数の利用者から「口座で勝手に取引が行われた」との報告が寄せられた
- 被害者からは、ハッカーを名乗る者から直接メールが届き、「GMO側が交渉に応じなかったため口座の残高を消した」と主張する事例も報告された

**影響範囲**:
- GMOクリック証券、OANDA証券など、複数のFX業者の顧客が影響を受ける可能性
- サーバー2万6,000件超に影響の可能性
- 被害額は数千万円規模と推定

**この事例が示すこと**:
- ユーザーが強いパスワードを使っていても、**サーバー側が侵害されれば認証情報が丸見え**
- パスワードを「解読」したのではなく、**サーバー上のファイルから直接読み取った**可能性が高い
- パスワードマネージャーで32文字の強力なパスワードを使っていても、この種の攻撃では防げない

### 事例2：2020年10月 GMOクリック証券 不正アクセス

**概要**: GMOクリック証券の顧客口座に不正アクセスがあり、149万円が流出。

**何が起きたか**:
- 何者かが不正に取得したIDとパスワードでログイン
- 出金先銀行口座を変更し、不正に出金
- 社内からIDやパスワードが流出した痕跡は見られなかった

**この事例が示すこと**:
- 認証情報の流出経路は不明だが、フィッシングやインフォスティーラー、他サービスからのパスワード再利用などが考えられる
- 当時、出金先変更に二段階認証がなかったことが問題の一因
- 事後対策として、出金関連の手続きに二段階認証を導入することを発表

### 2つの事例の比較

| 項目 | 2020年 GMOクリック証券 | 2026年 お名前.com デスクトップクラウド |
|---|---|---|
| 攻撃の入口 | 認証情報の不正取得（ID・パスワード） | サーバーへの不正アクセス（不正プログラム設置） |
| パスワード強度との関係 | 関係あり（弱いパスワードや使い回しが原因の可能性） | 関係なし（サーバー上のファイルから直接読取） |
| 被害額 | 149万円（1口座） | 数千万円規模と推定（複数口座） |
| 根本原因 | 認証情報管理の不備 | サーバーのセキュリティ管理不備 |
| 対策の主体 | ユーザー（使い回し禁止）+ 業者（MFA導入） | 業者（サーバー管理・脆弱性対策） |

## 大手サービスの不正アクセス事例

### 結論

**起きる。ただし「Apple や Google のサーバーが破られて、あなたのパスワードやパスキーが抜かれた」という形では、ほとんど起きていない。** 実際に起きているのは次の3パターンである。

1. **外部ベンダー経由**（自社ではなく取引先のシステムから）
2. **従業員個人を狙った攻撃**（フィッシング・電話・マルウェア）
3. **利用者側のアカウント乗っ取り**（使い回し・偽サイト・情報窃取マルウェア）

「壊されるのは金庫ではなく住人」というのが実態に近い。

### 直感：金庫と住人

巨大テック企業の認証基盤は、狙われる前提で設計された分厚い金庫である。だから攻撃者は金庫を正面から破ろうとせず、**鍵を持っている人（従業員）に電話して、鍵を渡してもらう**方向に回る。

これは比喩ではなく、2025年に Google 自身が受けた被害で実際に起きたことである。攻撃者は**電話で偽の IT 部門を装い、従業員から認証情報を聞き出す**（ビッシング）ことで、Google が広告主向けに使っていた Salesforce 環境に侵入した。漏れたのは中小企業の連絡先やメモで、広告アカウントや決済情報は対象外とされている。

### 4つの事例

| 時期 | 何が起きたか | 破られたのは |
|---|---|---|
| 2014年 | iCloud の著名人写真流出。フィッシングと標的型攻撃で**個別アカウント**に侵入したもので、iCloud 基盤が丸ごと破られたわけではない | 個々のアカウント |
| 2022年 | **LastPass** が全顧客の保管庫（vault）のバックアップを窃取された。パスワード自体はマスター鍵由来で暗号化されており、マスターパスワードは保持していなかった。ただし**サイト URL は暗号化されていなかった** | ベンダー（開発環境経由） |
| 2024年 | **Snowflake** 利用企業（AT&T、Ticketmaster など）が大量被害。調査の結果、**Snowflake の環境自体は侵害されておらず、顧客の認証情報が窃取されていた**（MFA 未設定のアカウントが狙われた） | 顧客側の認証情報 |
| 2025年 | Gmail の「大規模漏洩」報道。Google は**これを否定**し、回った 1.83 億件は**情報窃取マルウェアのログと過去の漏洩データの寄せ集め**だったと説明 | Google の基盤ではなく利用者側 |

### なぜ大手でも破られるのか（構造的な3理由）

1. **攻撃面が従業員の数だけある** — 何万人もの従業員の1人が騙されれば侵入される。Google の事例はまさにこれ
2. **自社で完結していない** — 認証・CRM・ログ管理などを外部委託しているので、**取引先の事故が自社の事故になる**。Snowflake はこの典型
3. **漏洩した認証情報が使い回される** — どこかで漏れたメールアドレスとパスワードの組を、片っ端から他サービスに試す（クレデンシャルスタッフィング）。Google は侵害されたパスワードを4億件規模のデータと照合して警告する仕組みを持ち、照合は暗号化したまま行うため Google にも平文は見えない

### あなたの保存先整理への示唆

- **保存先ベンダーが破られても、中身は読めない設計**。パスキーの秘密鍵もパスワードマネージャの保管庫も端末側でエンドツーエンド暗号化されている
- **それでも「どこに何を保存したか」は漏れうる**。LastPass の URL 非暗号化がそう。緊急度は高くないが、統一する動機にはなる
- **本当に怖いのは、自分のアカウントが狙われること**。パスキーはこの最大の攻撃経路（偽サイト・ビッシング）に構造的に強い。ドメインが違えば署名が作れないから
- **パスワードの使い回しを1つでも残すと、そこが一番弱い場所になる**。保存先の統一より先に、使い回しの解消を優先したほうが効果は大きい

## vaultwardenのパスキー対応状況

### 現状（2025年10月時点）

**できること**:
- WebAuthn/Passkeyを使ってvaultwarden自体にログインする（2FAとして）
- つまり「vaultwardenを守るためのパスキー」は使える

**できないこと**:
- 他のサービスのパスキーをvaultwardenのvaultに保存する（Bitwarden公式が2025年11月に対応した機能）
- vaultwardenのGitHub Discussionでも「vaultwarden does not support sign-in with passkeys (yet)」と明記

### ローカルバックアップの現実的な選択肢

| 方法 | メリット | デメリット |
|---|---|---|
| ハードウェアセキュリティキー（YubiKey等） | オフライン・物理的に所有。Googleが死んでも使える | 紛失時のリスク。1台数千円 |
| 複数のパスキー登録（Google + ハードウェアキー） | どちらかが使えればOK。最も実用的 | 管理が増える |
| Google Password Managerのエクスポート | Android から対応他社マネージャへは可能 | 保存先によっては不可 |
| Appleのパスキーを残しておく | 実質的なバックアップになる | 管理が分散する |

### vaultwardenへの期待

vaultwardenはBitwarden互換の非公式実装なので、公式Bitwardenがパスキー管理に対応した（2025年11月）ことを考えると、vaultwardenも近いうちに対応する可能性は高い。ただし、有志のOSSプロジェクトなので、公式ほどのスピードは出ない。

4. パスキーを移行するとき、なぜ「追加 → 確認 → 削除」の順なのか
   → 確認前に削除すると**ロックアウトする**から

## まとめ

### パスワード認証について
- 英数字+記号12文字以上は最低基準
- 「人間が考えた12文字」は辞書攻撃で破られることがあるので、**パスワードマネージャーが生成したランダムな12文字以上**が理想
- ハッシュは不可逆だが、攻撃者は同じハッシュになるまで手元で総当たりする。高速ハッシュは特に弱く、ソルトと低速 KDF（Argon2 / bcrypt / PBKDF2）で計算コストを上げる必要がある。1,000 万語の照合が SHA-256 で約 7.8 秒、PBKDF2 で約 5.4 日と、方式ひとつで 5 桁以上変わる
- パスキーが使えないサービスでは、vaultwardenに強力なパスワードを保存しておくのが現実的

### パスキーについて
- **仕組み**: パスワードの代わりに、端末の安全領域にしまった秘密鍵で署名する。デバイス固定型では秘密鍵は端末の外に出ず、同期型では暗号化された状態で別端末へ同期される。署名はドメイン名に縛られるため、フィッシング・リプレイ攻撃に構造的に強い
- **守れるもの**: サーバー漏洩、使い回し、推測
- **残るリスク**: 「端末紛失」や「Google アカウント侵害」は別のリスクとして残る

### 保存先と移行
- **保存先の選び方**: 2台体制では Apple 統一は不可。無料なら Google パスワードマネージャ、Mac の Safari も使うなら 1Password（無料枠は Bitwarden）。理想は「主系1つ + 予備1つ」で、まず一覧化する
- **移行の原則**: 「追加 → 別端末で確認 → 削除」の順を守る。逆順にするとロックアウトする。パスワードと2要素認証の経路は残す
- **複数パスキー**: 暗号学的には独立。理想は「1サービスあたり2つ以内」

### 大手事例の示唆
- 攻撃されるのは金庫（認証基盤）ではなく住人（従業員・顧客）。外部ベンダー経由・従業員へのビッシング・認証情報の使い回しが実態
- 保存先ベンダーが破られても中身は読めない設計だが、URL などのメタデータは漏れうる
- 最大の対策は使い回しの解消

### 実践的な落とし所

```
パスキー対応サービス → Google Password Managerで一元管理
パスキー非対応サービス → vaultwardenに強力なランダムパスワードを保存
Googleアカウント自体 → パスキーまたはセキュリティキーで保護
```

### Googleアカウントの保護（Google一元管理の場合）

1. Googleアカウントパスキー/MFAを最強に設定（パスワードログインは無効化できるなら無効化）
2. Android端末の画面ロックを強力に（6桁以上のPINまたは生体認証）
3. Googleのログイン履歴を月1回確認（進捗確認機能）
4. 端末紛失時の対応を決めておく（Find My Deviceでリモート消去できることを確認）

*本資料は会話内容をまとめたものである。仕様や対応状況は変更されるため、導入前に各社の公式ドキュメントを確認すること。*
