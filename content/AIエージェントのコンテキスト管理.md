## 概要

AIエージェントにおける[[コンテキスト]]の概念、[[コーディングエージェント]]と[[チャットエージェント]]での管理方法の違い、効果的な[[コンテキストエンジニアリング]]の原則を説明する。

## コンテキストとは

### 定義

AIエージェントにおけるコンテキストは、モデルが適切な応答生成するために必要な**最小限のデータセット**である。計算機科学では「タスクコンテキスト」と呼ばれ、タスクが中断され、後で同じポイントから再開できるようにするために保存される最小限のデータを指す（参照: [Wikipedia - Context (computing)](https://en.wikipedia.org/wiki/Context_(computing))）。

### コンテキストの役割（3軸）

| 軸 | 説明 | 例 |
|-----|------|-----|
| **情報の範囲指定** | 「何について答えるべきか」を定義 | プロジェクトのコードベース、ユーザーの質問 |
| **行動の制約** | 「どのように答えるべきか」を規定 | コーディング規約、出力形式の指定 |
| **状態の維持** | 会話やタスクの経緯を保持 | 会話履歴、以前の操作結果 |

### コンテキストの構成要素

```
システムプロンプット（役割・動作規則）
    ↓
コンテキスト（プロジェクト情報、コードベース構造）
    ↓
インストラクション（具体的なタスク指示）
    ↓
入力（ユーザーの入力）
```

## エージェントタイプ別 コンテキスト管理の違い

### 基本的な違い

| 観点 | コーディングエージェント | チャットエージェント |
|------|--------------------------|---------------------|
| **文脈の主成分** | コード、ファイル構造 | 会話、個人情報 |
| **指示の永続化** | CLAUDE.md、ルールファイル | メモリ機能 |
| **動的文脈** | ツール結果、git差分 | 会話履歴 |
| **管理必要性** | 高（コンテキストプルーニング必要） | 低（自然に蓄積） |
| **取得方法** | ジャストインタイム検索（JIT） | 推論前取得（事前埋め込み） |
| **記憶の範囲** | プロジェクト/ワークスペース単位 | ユーザー単位（全会話） |

### コーディングエージェント（Claude Code等）

#### テンプレート構造

```
1. CLAUDE.md（プロジェクト指示）
   - ビルドコマンド、テスト手順
   - コーディング規約、アーキテクチャ
   - 常に守るべきルール

2. システムプロンプット
   - 役割定義（コーディングアシスタント）
   - ツール使用規則

3. コードベース文脈
   - ファイル構造、シンボル情報
   - 現在のファイル、カーソル位置

4. 会話履歴
   - ユーザーの要求と以前の操作
```

#### 特徴

- **永続的指示**: CLAUDE.mdファイルでプロジェクト固有のルールを保存
- **パスマッチング**: `.claude/rules/`でファイルタイプに応じたルールを適用
- **ツール結果の管理**: ファイル読み取り、grep結果などを動的に取得・クリア
- **コンテキストプルーニング**: 古いツール結果を削除して容量を確保

> [!tip] Claude CodeのCLAUDE.md
> CLAUDE.mdは200行以内に収めることが推奨される。長すぎるファイルはコンテキストウィンドウを圧迫し、指示の準拠率が低下する（参照: [Claude Code Memory](https://docs.anthropic.com/en/docs/claude-code/memory)）。

### チャットエージェント（ChatGPT、Claude等）

#### テンプレート構造

```
1. システムプロンプット
   - 役割と動作規則

2. 会話履歴
   - ユーザー/アシスタントの交互メッセージ

3. アタッチメント
   - ドキュメント、画像等

4. メモリ
   - ユーザーの設定、個人情報
```

#### 特徴

- **会話の線形蓄積**: 新しいターンが以前の会話に追加される
- **グローバルメモリ**: ユーザーの設定や好みを全会話で保持
- **FIFOローリング**: 古いメッセージが自動的に削除される

## コンテキストテンプレート

### 基本構造（XMLタグ使用）

Anthropicのベストプラクティスでは、XMLタグでコンテキストを構造化することが推奨される（参照: [Prompt Engineering Best Practices](https://docs.anthropic.com/en/docs/build-with-claude/prompt-engineering/claude-prompting-best-practices)）。

```xml
<system_prompt>
  役割と動作規則
</system_prompt>

<context>
  プロジェクト情報、コードベース構造、制約事項
</context>

<instructions>
  具体的なタスク指示（番号付きステップ推奨）
</instructions>

<examples>
  入出力例（3〜5個）
</examples>

<input>
  ユーザーの入力
</input>
```

### モデル別の違い

| モデル | 特徴 | コンテキスト設計の注意点 |
|--------|------|--------------------------|
| **Claude Opus 5** | デフォルトで思考機能オン、冗長な傾向 | 冗長さを制御する指示が必要 |
| **Claude Fable 5.1** | エージェント作業中にユーザー向け進捗報告が少ない | 進捗報告を明示的に指示 |
| **Claude Sonnet 5** | 簡潔、思考深度の調整に敏感 | 簡潔さは默认だが、思考深度の調整が有効 |
| **GPT-5.x** | 272k〜1Mトークン、独自のキャッシュ戦略 | キャッシュ戦略の違いを理解 |

> [!note] モデルによる違い
> モデルが異なっても、コンテキストの役割（情報の範囲指定、行動の制約、状態の維持）は共通。モデルの違いは「どの程度詳細な指示が必要か」「どのような構造が効果的か」に現れる。

## コンテキスト最小化の原則

### なぜ最小限が必要か

1. **計算コストの問題**
   - アテンションメカニズムはO(n²)の計算コスト
   - コンテキストが大きいほど処理が遅くなり、コストが増加
   - 200kトークン vs 1Mトークンでは数百倍の計算差

2. **コンテキストロットの防止**
   - トークン数が増えるとモデルの精度が低下する現象
   - コードは自然言語よりもトークン密度が高く、この問題が顕著
   - ツール結果（ファイル読み取り、grep結果等）が大量に蓄積すると問題に

3. **効果的なコンテキストエンジニアリング**
   - Anthropicは「**最小限の高シグナルトークン**」で最大の結果を出すことを推奨
   - *"find the smallest possible set of high-signal tokens that maximize the likelihood of your desired outcome"*

### 推奨事項

| 項目 | 推奨 | 根拠 |
|------|------|------|
| **CLAUDE.mdファイル** | 200行以内 | 準拠率の低下防止 |
| **メモリファイル** | 200行または25KB以内 | コンテキストウィンドウの効率的利用 |
| **システムプロンプット** | 簡潔で明確に | 計算コストの削減 |
| **ツール結果** | 古いものはクリア | コンテキストロットの防止 |
| **例（few-shot）** | 3〜5個 | 効果と多様性のバランス |

### Before/After 比較

```
Before: システムプロンプット + 全会話履歴 + 全ツール結果 → コンテキストロット発生
After:  最小限のシステムプロンプット + 直近の会話 + 必要なツール結果のみ → 高精度維持
```

## 実例：Claude Codeのコンテキスト管理

### CLAUDE.mdのスコープ

| スコープ | 場所 | 用途 |
|----------|------|------|
| **管理ポリシー** | `/Library/Application Support/ClaudeCode/CLAUDE.md` | 組織全体の指示 |
| **ユーザー指示** | `~/.claude/CLAUDE.md` | 個人の設定 |
| **プロジェクト指示** | `./CLAUDE.md` | チーム共有の指示 |
| **ローカル指示** | `./CLAUDE.local.md` | 個人のプロジェクト設定 |

### パスマッチングルール

```markdown
---
paths:
  - "src/api/**/*.ts"
---

# API開発ルール
- すべてのAPIエンドポイントには入力バリデーションを含める
- 標準エラーレスポンス形式を使用
```
