## 概要

EKS 基盤（prod / dev / stg）のコスト最適化を前提に、AWS の Reserved Instance（RI）と Savings Plans（SP）の違い、適用順序、休日夜間停止環境での購入判断、環境別の使い分けを整理する。

## 結論（先に3行）

1. **RI と SP はどちらも「1年 or 3年のコミットと引き換えの割引」**。違いは *何を固定するか*。RI はインスタンス属性、SP は **1時間あたりの金額（$/時間）**。
2. **買うのは「24時間365日動き続けている下限（床）」だけ**。休日夜間停止する dev/stg は対象外。
3. **dev/stg = Spot ＋ 夜間停止、prod = 床だけ Compute SP ＋ ピークはオンデマンド**、が基本形。

## 基礎 — 何を固定するかの違い

| | 固定するもの | イメージ |
|---|---|---|
| **Reserved Instance (RI)** | インスタンスの属性（ファミリー／サイズ／リージョン／必要なら AZ） | 「特定の区画を1年押さえる駐車場契約」 |
| **Savings Plan (SP)** | 1時間あたりの金額（$/時間） | 「毎時この金額は必ず使う」というサブスク契約 |

**比喩の限界（重要）**：RI も SP も **途中解約できない**。Standard RI にはマーケットプレイス転売という逃げ道だけがある。「使わなくなったら返せる」はどちらにも当てはまらない。

**仕組みの核心**：SP は $4.00/時 と契約したら、昼も夜も土曜も、1時間ごとに $4.00 分の枠が存在し、**使われなければ捨てられる**。対象利用が枠を超えた分だけオンデマンド課金。

> つまり SP は「利用の **谷** に合わせて買う」ものではなく「**谷を底上げする**」もの。
> 谷に合わせた超過コミットは、ほぼ確実に回収できない。

## 種類と最大割引率

| 種類 | 最大割引 | 適用対象 | 柔軟性 |
|---|---|---|---|
| **Compute Savings Plans** | 66% | EC2・Fargate・Lambda | ファミリー／サイズ／AZ／リージョン／OS／テナンシーすべて自動追従 |
| **EC2 Instance Savings Plans** | 72% | EC2 のみ | ファミリー＋リージョンを固定。サイズ／OS／テナンシーは追従 |
| **SageMaker AI Savings Plans** | 64% | SageMaker AI | ファミリー／サイズ／リージョン／機能を追従 |
| **Database Savings Plans**（2025年12月〜） | 35% | RDS・Aurora・DynamoDB・ElastiCache・DocumentDB・Neptune・Timestream・DMS・OpenSearch | 1年・前払いなし。エンジン／ファミリー／サイズ／AZ／リージョン／サーバーレスを追従 |
| **Standard RI** | 72% | EC2 等 | 固定。**転売可**（リージョナル／ゾーナル） |
| **Convertible RI** | 66%（実勢は更に低い） | EC2 等 | ファミリー／サイズ／OS／テナンシーを**差額交換**で変更可。転売不可 |

- 最大割引率は **3年・全前払い**などの最良ケースの数字。実際の率は「期間・支払条件・ファミリー・リージョン」で変わる。
- SP の価格は **コミット額の大小では変わらない**。

## RI と SP の比較表

| 観点 | Compute SP | EC2 Instance SP | Standard RI（リージョナル） | Standard RI（ゾーナル） |
|---|---|---|---|---|
| 最大割引率 | 66% | 72% | 72% | 72% |
| 適用対象 | EC2・Fargate・Lambda | EC2 のみ | EC2 のみ | EC2 のみ |
| コミット単位 | $／時間 | $／時間 | インスタンス数 | インスタンス数 |
| インスタンスファミリー | 自動追従 | 固定 | 固定 | 固定 |
| リージョン | 自動追従 | 固定 | 固定 | 固定（AZ も固定） |
| インスタンスサイズ | 自動追従 | 自動追従 | 自動追従※ | 固定 |
| OS／テナンシー | 自動追従 | 自動追従 | 固定 | 固定 |
| Fargate / Lambda | あり | なし | なし | なし |
| キャパシティ予約 | なし | なし | なし | **あり** |
| マーケットプレイス転売 | 不可 | 不可 | 可（残り1か月以上） | 可（残り1か月以上） |
| 期間 | 1年／3年 | 1年／3年 | 1年／3年 | 1年／3年 |

※リージョナル Standard / Convertible RI のサイズ柔軟性は **Linux/UNIX・共有テナンシー** が条件。

## 適用順序とスコープ

**適用順序**（二重適用はない）:

```
RI → EC2 Instance SP → Compute SP
```

節約率の高い組み合わせから消費される。Consolidated Billing 配下では、まずオーナーアカウントの利用に充当され、その後メンバーアカウントへ（共有が有効な場合）。

**割引が効かないもの**:

- **Spot**（そもそも最大90%引き。SP の対象外）
- **EKS コントロールプレーン**（$0.10/時/クラスタ）。ただし EKS 上の **EC2 ワーカーノードは対象**
- Dedicated Instance の $2/時 の専用料金
- RI で既にカバーされた利用

## よく混同される境界

### 割引 ≠ キャパシティ確保
- **ゾーナル RI** だけがキャパシティを確保する。リージョナル RI と SP は確保しない。
- キャパシティが必要なら **On-Demand Capacity Reservation (ODCR)** を使い、そこに SP やリージョナル RI を重ねて割引する（ODCR 自体は使わなくてもオンデマンド相当額が課金される）。

### RI は「legacy」になりつつある
- AWS 自身が RI を「古い／legacy な購入オプション」と位置づけ、**新しいインスタンスファミリーでは RI 料金が用意されていない場合がある**と明記。
- データベース系の多くは Database Savings Plans でカバーされるようになった。
- RI が主役として残るのは **Redshift の Reserved Nodes（プロビジョンド、最大75%）** など、まだ SP が存在しない領域。
- **同じワークロードに Database SP と RDS RI の併用は不可**（別ワークロードへの振り分けは可）。

### RI の制約
- 転売できるのは **Standard のリージョナル／ゾーナルのみ**、**残存1か月以上**、**売り手の登録銀行口座が米国住所**、**手数料は前払い価格の12%**。
- Convertible RI、RDS / ElastiCache の RI は転売不可。

## 休日夜間停止の環境でも買うべきか

### 損益分岐の式（覚えておく価値あり）

あるワークロード **だけ** をカバーするプランを買う場合、有利になる条件は:

> **稼働率 > 1 − 割引率**

- 割引 30% → 稼働率 **70%** 超が必要
- 割引 50% → 稼働率 **50%** 超が必要
- 割引 66% → 稼働率 **34%** 超で有利（3年・全前払いの最良ケースのみ）

### dev/stg の稼働率

平日12時間 × 週5 × 52週 = **3,120h / 8,760h = 約 35.6%**

→ 損益分岐を越えるには **64.4% 超の割引** が必要。Compute SP の上限 66% は最良ケースでしか出ないので、現実には届かない。

dev/stg 単独でコミットを買うと（例: $1.40/h）、オンデマンド $6,240 に対し $12,264 で **約2倍の支払い**。止めれば課金ゼロのオンデマンドと、止めても請求が続くコミットは、そもそも相性が悪い。

### 試算（説明用の仮定: prod $5.00/h 24/365、dev/stg $2.00/h 平日12時間、割引 30%）

| ケース | 年間コスト | 無コミット比 |
|---|---|---|
| 無コミット（全オンデマンド） | $50,040 | — |
| **A: prod の下限だけ買う（$3.50/h）** | **$36,900** | **−$13,140** |
| B: 全体の平均で買う（$4.00/h） | $39,046 | −$10,994（A 比 **+$2,146 損**） |
| C: 両方をカバーする（$4.90/h） | $42,924 | −$7,116（A 比 **+$6,024 損**） |

**B が A に負ける理由**：B は夜間に $0.50/h の枠を 5,640h てており（−$2,820）、その代わり平日日中の追加割引は +$668 しかない。**谷に合わせた超過コミットは回収できない。**

## 環境別の三層モデル

```
[ ピーク・突発スパイク ]  ──>  On-Demand（コミットせず、使った分だけ払う）
[ バッチ・非同期 Worker ]  ──>  Spot（prod でも中断許容できる処理に適用）
[ 24/365 の常時稼働床   ]  ──>  Savings Plans（Compute SP 1年が基本）
──────────────────────────────────────────────
[ dev / stg 環境        ]  ──>  Spot ＋ 休日夜間停止
```

| 対象 | 推奨 | 削減率の目安 | コミット | 中断リスク | 運用のツボ |
|---|---|---|---|---|---|
| dev / stg | Spot（＋夜間停止） | 最大 90% | なし | あり（許容） | NodePool で広いファミリーを許可 |
| prod の常時稼働床 | Compute SP（1年） | 約 25〜66% | 1年推奨 | なし | **最も低い時間帯の床**だけ購入 |
| prod のピーク・スパイク | On-Demand | 0% | なし | なし | コミット超過分は自動でこれになる |
| prod の耐障害バッチ | Spot | 最大 90% | なし | あり（要設計） | 再スケジュール可能な Pod に限定 |

### RI を選ばない理由
Karpenter でファミリーが動的に変わり、Graviton（ARM）移行も視野に入るなら、**ファミリーを固定する EC2 Instance SP / RI は相性が悪い**。Compute SP ならリージョン・ファミリー・OS・テナンシーを横断して自動追従する。

## 運用のツボ

### dev / stg（Spot ＋ 夜間停止）
- Spot 最大90%引き × 稼働時間 35% ≒ オンデマンド常時稼働比で **約96%削減**。
- Karpenter の `NodePool` で `karpenter.sh/capacity-type: ["spot"]` を指定し、インスタンスファミリーを広めに許可（`c6i`, `c7i`, `c6a`, `m6i`, `m7g` など）しておくと在庫切れによる起動失敗をほぼゼロにできる。

### prod（床だけ SP）
- 買う規模は「**最も利用が落ち込む夜間・週末の床**」だけ。日中ピークに合わせると夜間の未使用枠を払い続けることになる。
- ピーク分はあえてオンデマンドのまま放置。SP のコミットを超えた分は自動的にオンデマンド料金で計算される。

### 購入の進め方
1. Cost Explorer を **時間別・日別** で見て、24/365 で必ず動いている床の金額を出す（これが購入額の上限）
2. **Savings Plans Purchase Analyzer** に実績を食わせて推奨コミット額と削減見込みを確認（割引率は条件で変わるため、本メモの%は目安）
3. まず prod の床ぶんだけ **1年・前払いなし・小口** で購入
4. dev/stg はオンデマンド＋Spot のまま、夜間停止を徹底
5. 3か月後に **Utilization（利用率）と Coverage（カバー率）** を見て、谷が埋まっていれば積み増し
6. **SP は後から積み増しできる**（条件変更は不可）。いきなり大きく買わない

## チェックリスト

- [ ] 買う対象は「24/365 動いている床」に限定したか
- [ ] 対象ワークロードの稼働率は `1 − 割引率` を上回るか
- [ ] Karpenter / Graviton 移行の予定があるなら Compute SP を選んだか
- [ ] キャパシティ確保が要件なら、割引とは別に ODCR を検討したか
- [ ] EKS コントロールプレーン・Spot・Dedicated 料金が対象外であることを織り込んだか
- [ ] 期間は 1年で始めたか（3年は構成変更の予定がない場合のみ）
- [ ] 購入前に Purchase Analyzer の数字を確認したか

## まとめ

- コミットを買うのは **24/365 で動き続ける「床」だけ**。休日夜間停止する dev/stg には買わない。
- dev/stg は **Spot ＋ 夜間停止**、prod は **床ぶんの Compute SP（1年・前払いなし・小口）＋ ピークはオンデマンド**が基本形。
- ファミリーを固定したくない（Karpenter / Graviton 移行）なら RI ではなく Compute SP。キャパシティ確保が要件なら割引とは別に ODCR を検討する。

## 前提と免責

- 第6章の試算は理解のための **仮定値**（prod $5.00/h、dev/stg $2.00/h、割引30%）に基づく。実際の数値は自環境の Cost Explorer で置き換えること。
- 割引率は期間・支払条件・インスタンスファミリー・リージョンで変動する。本メモの最大割引率は AWS 公表の最良ケース値。
- 料金体系・対象サービスは変更される。購入判断の直前に一次情報を確認すること。
